# Chain of Responsibility (Цепочка ответственности)

![Chain of Responsibility Diagram](https://refactoring.guru/images/patterns/diagrams/chain-of-responsibility/solution1-en.png?id=dccad3e628bd2b8f1856c99369ca6e5b)

## Суть паттерна

**Chain of Responsibility** — поведенческий паттерн, который позволяет передавать запросы последовательно по цепочке обработчиков. Каждый обработчик решает: обработать запрос самостоятельно или передать его следующему звену в цепи.

```
Запрос → [Handler 1] → [Handler 2] → [Handler 3] → Обработан / Отклонён
```

## Участники

| Участник | Описание |
|----------|----------|
| **Handler** | Интерфейс/абстрактный класс с методом обработки запроса и ссылкой на следующий обработчик |
| **ConcreteHandler** | Конкретная реализация: решает, может ли обработать запрос, и передаёт его дальше при необходимости |
| **Client** | Инициатор запроса, формирует цепочку и отправляет запрос любому её звену |

## Когда применять

Разные типы запросов обрабатываются разными способами, но порядок и типы заранее неизвестны  
Нужно выполнить несколько проверок/действий в строгом порядке (аутентификация → валидация → кэширование → бизнес-логика)  
Состав и порядок обработчиков может меняться динамически во время выполнения  

## Преимущества

-  **SRP**: каждый обработчик отвечает за одну задачу
-  **OCP**: новые обработчики добавляются без изменения существующего кода
-  **Гибкость**: цепочку можно собирать и перестраивать динамически
-  **Порядок**: вы контролируете последовательность обработки

## Особенности

- Запрос может остаться необработанным, если дойдёт до конца цепочки без подходящего хендлера
- Отладка может быть сложнее из-за динамической природы цепочки

# Chain of Responsibility: Маршрутизация пациентов

## Архитектура решения

```
Пациент → RegistryHandler → TherapistHandler → SpecialistHandler → [Конец цепочки]
```

## Компоненты паттерна в коде

**Абстракция**
- `MedicalHandler` — интерфейс с методами `handle()` (обработка запроса) и `set_next()` (связь со следующим звеном)
- `BaseHandler` — базовая реализация: хранит ссылку `_next` и передаёт запрос дальше, если не обработал сам

**Конкретные обработчики**
| Класс | Зона ответственности | Условие обработки |
|-------|---------------------|------------------|
| `RegistryHandler` | Первичный фильтр | Нет симптомов и не нужен плановый осмотр |
| `TherapistHandler` | Терапевтические случаи | Плановый осмотр без симптомов; простуда; лёгкая головная боль |
| `SpecialistHandler` | Узкие специалисты | Симптом есть в словаре `_ROUTES` (зубная боль, сердце, зрение и др.) |

**Модель данных**
- `PatientForm` — содержит имя пациента, флаги симптомов/осмотра и стандартизированный маркер симптома

## Поток выполнения

1. Клиент создаёт цепочку в строгом порядке: `Registry → Therapist → Specialist`
2. Вызывает `handle()` у первого обработчика с объектом `PatientForm`
3. Каждый обработчик проверяет условия:
   - Если запрос подходит — возвращает результат (строка с инструкцией)
   - Если нет — вызывает `super().handle()`, передавая запрос следующему звену
4. Если цепочка закончилась без обработки — возвращается `None`
